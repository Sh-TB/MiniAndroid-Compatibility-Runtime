BASE ANDROID FOUNDATION — COMPLETE PLATFORM CONTRACT AUDIT

PURPOSE

This is a foundation task, broader than #373. Do NOT keep fixing individual white/black/partial APK failures before the Android base contract is complete enough to understand an unknown APK.
Required chain: APK -> package -> install -> identity -> permissions -> sandbox -> storage -> Context -> system services -> Binder/IPC -> components -> lifecycle -> Intent resolution -> resources/configuration -> main thread -> window/View -> graphics/surface -> input -> network -> media -> native/ABI -> persistence -> verification.

NON-NEGOTIABLE

Do not make apps run by granting every permission, advertising every ABI, returning every feature as supported, returning fake system services, bypassing SecurityException, giving apps root, sharing private storage, bypassing exported/signature checks, swallowing missing-service failures, or pretending unsupported GLES/Vulkan/native execution works.
Capabilities must be honest and machine-readable.

1. PLATFORM / DEVICE CONTRACT

Build a machine-readable MiniAndroid environment profile covering API level, VERSION.SDK_INT, VERSION.RELEASE, VERSION_CODES behavior gates, Build.*, device/model/manufacturer/product/board/fingerprint, system properties, locale/language/country, timezone/clock, 12/24-hour settings, display width/height, density/dpi/scaledDensity/fontScale, orientation, smallestWidth/screenWidth/screenHeight, screen-size class, uiMode/night mode, touch/keyboard/navigation configuration, display ID/state, refresh rate and color mode.
Every capability must record ADVERTISED / IMPLEMENTED / TESTED / EXECUTABLE.

2. CPU / ABI / NATIVE FOUNDATION

Audit host CPU, executable CPU, 32/64-bit process model, supported and actually executable ABIs, native bridge/translator and version, ELF class/machine/ABI, PT_LOAD alignment/page size, DT_NEEDED dependency closure, JNI registration, native loader, linker namespaces, symbol resolution, nativeLibraryDir, argv/environment semantics and executable permissions.
Never report arm64 as executable unless arm64 code really executes. Unsupported native ABI must become a preflight blocker: ABI_MISMATCH_TRANSLATION_REQUIRED.

3. PACKAGE MANAGER / INSTALLATION

Implement/verify packageName, versionCode/versionName, ApplicationInfo, ActivityInfo, ServiceInfo, ReceiverInfo, ProviderInfo, PermissionInfo, signatures/signing identity, sharedUserId, process names, exported/enabled state, directBootAware, launch modes, metadata, intent filters, queries/package visibility, uses-sdk, uses-feature, uses-library, uses-native-library, supports-screens, uses-configuration, sourceDir/publicSourceDir, splitSourceDirs, nativeLibraryDir, dataDir, deviceProtectedDataDir, credentialProtectedDataDir, codeCacheDir, install/update/uninstall state.
Installation must create real package state. APK parsing is not installation. Installation is not execution.

4. APK STRUCTURAL PREFLIGHT

Inspect AndroidManifest.xml, classes*.dex, resources.arsc, res/, assets/, lib/, META-INF/, split metadata and native ELF files.
Extract SDK min/target/max API, all components and entry points, exported state and intent filters; native ABIs/libraries/DT_NEEDED/JNI/load paths; resource packages/splits/configurations/densities/languages/overlays/assets/fonts/XML/drawables; and implied requirements such as WebView, SQLite, media, camera, microphone, sensors, network, external storage, foreground services, alarms, notifications, accessibility, overlay, providers, FileProvider/content URIs, dynamic loading, reflection and native loading.
Classify every requirement as REQUIRED / OPTIONAL / CONDITIONAL / IMPLIED / UNKNOWN.

5. PERMISSION FOUNDATION

Implement a real permission state machine for normal, dangerous/runtime, signature, signature|privileged, development, installer/system, special-access and AppOps-controlled operations.
Track requested, declared, granted, denied, request-pending, user decision, revocation and API-version semantics.
Every protected operation must follow: caller UID -> package -> declaration -> grant -> AppOps/special access -> user/profile policy -> API policy -> allow/deny/error.
Do not use a universal permission=true.

6. PACKAGE / USER / UID / SECURITY IDENTITY

Model package, UID, GID, userId, profile, process, signing identity, shared UID and isolated process identity.
Two packages must not accidentally share private storage, UID, preferences, databases, providers, Context identity, process state or Binder identity.

7. FILESYSTEM / STORAGE

Create actual per-package storage, not path strings. At minimum model /data/user//, /data/user_de//, files, cache, code_cache, no_backup, databases, shared_prefs, app-specific external files/cache, shared external storage, APK/source paths and nativeLibraryDir.
Test create, exists, open, read, write, append, truncate, rename, delete, mkdir, recursive mkdir, stat, length, timestamps, file descriptors, locking, persistence, restart, reinstall, uninstall cleanup, package isolation, user isolation, path traversal and permission denial.
File.exists() and File.length() must reflect real filesystem state.

8. CONTEXT / CONTEXTIMPL

Audit application/package/Activity/Service/display/device Contexts, createPackageContext, createConfigurationContext, createDisplayContext, classloader, Resources, PackageManager, ContentResolver, data/database/shared-preference directories and getSystemService.
Wrong Context identity is a platform root.

9. SYSTEM SERVICES

Inventory at minimum ActivityManager, PackageManager, WindowManager, PowerManager, UserManager, PermissionManager, AppOpsManager, StorageManager, ConnectivityManager, AlarmManager, JobScheduler, NotificationManager, ClipboardManager, InputManager, SensorManager, LocationManager, CameraManager, AudioManager, MediaSession, Vibrator, Bluetooth, Wifi, Telephony, DownloadManager, Accessibility, DevicePolicy, Keyguard, Account services, ContentResolver/provider infrastructure and WebView-related services.
For each record SERVICE / API / IDENTITY / PERMISSION / STATE / ERROR MODEL / LIFECYCLE / IPC / IMPLEMENTED / TESTED / REAL APK / MISSING.
Never return fake non-null services just to suppress crashes.

10. BINDER / IPC

Audit service lookup, registration where needed, Binder identity, calling UID/PID, clearCallingIdentity/restoreCallingIdentity, Parcel, Parcelable, interface tokens, transactions, callbacks, death recipients, RemoteException, service unavailable and permission checks at the service boundary.

11. ACTIVITY / SERVICE / RECEIVER / PROVIDER / PROCESS

Activity: resolve, instantiate, attach, Context, Application, lifecycle, saved state, configuration changes, task/back, launch modes, result delivery.
Service: startService, foreground-service semantics where supported, bindService, ServiceConnection, lifecycle, process association.
Receiver: registration, resolution, delivery, lifecycle/timeout.
Provider: authority, attachInfo, URI resolution, permissions/path permissions, CRUD, openFile/openAssetFile, caller identity and lifecycle.
Process: package-to-process mapping, start, death, restart, multiple processes, importance, cold/warm startup.

12. INTENT / RESOLUTION

Implement explicit/implicit intents, action/category, URI/MIME, component/package, flags, extras, ClipData, selectors, filters, priority/default handlers, exported checks, permission checks, package visibility and activity/service/provider/receiver resolution. No app-specific intent routing.

13. RESOURCES / CONFIGURATION

Treat resources.arsc, AssetManager, asset paths, resource IDs/packages, split resource composition, overlays/RRO/idmap, locale, density, orientation, smallest width, screen size, night mode, API/version qualifiers, styles/themes, attributes, TypedArray, strings, arrays, dimensions, colors, ColorStateList, drawable/mipmap/raw, XML, fonts, NinePatch, vector, animated drawable and fallback/default resources as base platform infrastructure.
Resource selection must be deterministic and configuration-aware.

14. MAIN THREAD / SCHEDULING

Audit Looper, MessageQueue, Handler, HandlerThread, Runnable, delayed messages, main-thread identity, Executor, synchronization, Choreographer, frame callbacks, traversal scheduling, vsync abstraction, lifecycle ordering and reentrancy. No arbitrary sleep-based compatibility fixes.

15. WINDOW / VIEW / INPUT FOUNDATION

Core chain: Activity -> Window -> WindowManager -> WindowManagerGlobal -> ViewRootImpl -> DecorView -> ViewTree -> measure -> layout -> draw -> Surface.
Audit addView/removeView, ViewRoot attachment, DecorView ownership, requestLayout, invalidate, traversal, measure/layout/draw, dirty propagation, focus, touch/key dispatch, MotionEvent, pointer IDs, coordinate transforms, insets, system bars, window flags, visibility, alpha, clipping, matrix, elevation, z-order and hardware/software layers.
ViewTree existence is not visual success.

16. GRAPHICS / SURFACE / PRESENTATION

Audit View/Canvas/RenderNode -> Surface -> BufferQueue -> gralloc/backend -> SurfaceFlinger/compositor -> display -> capture.
Include Surface, SurfaceHolder, SurfaceView, GLSurfaceView, SurfaceTexture, TextureView, EGL, GLES, Vulkan, ANativeWindow, framebuffer, viewport, shader compile/link, texture upload/binding, swap, presentation, buffer format/size/usage flags, fences, back-pressure, surface generation/replacement, BLAST/transactions, HWC, composition, colorspace, alpha and secure/protected surfaces.
Track DRAWN -> BUFFER_QUEUED -> BUFFER_ACQUIRED -> COMPOSITED -> PRESENTED -> CAPTURED.
Do not equate EGL initialization with visible output.

17. INPUT / DEVICE FEATURES

Model touchscreen, mouse, keyboard, DPAD, gamepad, stylus, pointer capture, focus, key repeat, sensors, vibrator, device IDs and display IDs. Feature reporting must match actual capability.

18. NETWORK

Audit network, loopback, DNS, IPv4/IPv6, sockets, TLS, proxy, cleartext policy, connectivity callbacks, network capabilities, identity, permissions, offline behavior and timeout/error semantics. Do not fake network success.

19. MEDIA / AUDIO

Audit MediaPlayer, MediaCodec, MediaExtractor, MediaMetadataRetriever, AudioTrack, AudioRecord, AudioManager, MediaSession, audio focus, volume, codecs, MIME/container, sample formats, YUV/RGB, video Surface, synchronization and surface recreation.

20. HARDWARE / SENSOR CAPABILITIES

Inventory camera, microphone, location/GPS, accelerometer, gyroscope, magnetometer, proximity, light, pressure, temperature, step detector/counter, Bluetooth, Wi-Fi, NFC, USB, biometrics, telephony and vibration.
Each capability must be DECLARED / AVAILABLE / PERMITTED / FUNCTIONAL / OPTIONAL.

21. SYSTEM PROPERTIES / BUILD CONTRACT

Audit Build., VERSION., SUPPORTED_ABIS, CPU_ABI, device/model/manufacturer, graphics properties, GLES version/extensions, Vulkan properties, display properties, locale/timezone, API behavior flags and feature flags.
No false capability advertisement.

22. UNIFIED APK PRE-FLIGHT

Create one machine-readable prerequisite report covering PACKAGE, INSTALL, SDK/API, ABI, NATIVE, DEX, RESOURCES, FEATURES, PERMISSIONS, SYSTEM SERVICES, STORAGE, NETWORK, GRAPHICS, MEDIA, INPUT, CONFIGURATION, SECURITY and EXTERNAL DEPENDENCIES.
Each requirement is REQUIRED / OPTIONAL / CONDITIONAL / IMPLIED / UNKNOWN and compared against AVAILABLE / PARTIAL / MISSING / INCOMPATIBLE / NOT_TESTED.
Required JSON fields: package, sdk, components, permissions, special_access, features, abi, native, resources, splits, system_services, storage, network, graphics, media, input, configuration, security, environment, mismatches, blockers, verdict, first_divergence, execution_level.

23. PRE-FLIGHT MUST PRECEDE LAUNCH

For every unknown APK: inspect APK -> identify package -> inspect manifest -> inspect DEX -> inspect native -> inspect resources/assets -> inspect splits -> derive requirements -> inspect MiniAndroid environment -> compare -> classify blockers -> select execution mode -> install -> launch -> trace -> find first divergence -> classify environment/platform/runtime cause.
This is required for the Agent Skill too.

24. WHITE / BLACK / PARTIAL RECLASSIFICATION

Reclassify historical cases into ENVIRONMENT_MISMATCH, ABI_NATIVE, API_PLATFORM_CONTRACT, PACKAGE_INSTALL, PERMISSION_SECURITY, IDENTITY_SANDBOX, SYSTEM_SERVICE_IPC, RESOURCE_CONFIGURATION, COMPONENT_LIFECYCLE, VIEW_WINDOW, GRAPHICS_SURFACE, BUFFER_COMPOSITION, PRESENTATION, MEDIA, NETWORK, INPUT, CAPTURE_ONLY, ORDINARY_RUNTIME_ROOT or UNKNOWN.
Only genuine runtime roots remain in the ordinary root pipeline.

25. ROOT REGISTRY CROSS-MATCH

Before creating a root: A=already covered, B=same root/new evidence, C=existing root/missing sub-law, D=genuinely new platform root, E=environment prerequisite, F=future/out-of-scope.
Only C/D create new runtime-root work. E belongs to the foundation/environment matrix.

26. NEGATIVE SECURITY TESTS

Prove that MiniAndroid does NOT over-grant: denied permission, missing permission, signature mismatch, private storage access, cross-package file access, wrong UID, wrong user, unexported component, provider without permission, missing feature, unsupported ABI, missing native library, unavailable service, unavailable graphics feature, unavailable camera/microphone, unavailable network, unsupported API and incomplete split APK.
Failures must be deterministic and semantically honest.

27. REAL APK VALIDATION

Use independent families: pure DEX app; resource-heavy app; storage/database app; WebView app; ARM-native app; libGDX/game; media app; permission-heavy app; multi-component app; Telegram-class complex app; one random corpus app; one random corpus game.
Do not validate the foundation only against already-working apps.

28. EVIDENCE

Every foundation law requires STATUS, SOURCE, ANDROID LAW, IMPLEMENTATION, SYNTHETIC PROBE, REAL APK, FIRST DIVERGENCE, RUNTIME TRACE, ACTUAL STATE CHANGE, SCREENSHOT/PROVENANCE where visual, 3-RUN RESULT, REGRESSION RESULT and COMMIT.
Insufficient: exit code, APK parsed, PNG exists, process alive, EGL initialized, ViewTree exists or coder statement.

29. REQUIRED FINAL OUTPUT

Produce: Android Base Foundation inventory; implemented base capabilities; missing base capabilities; partial capabilities; false/incorrect capability advertisements; APK prerequisite matrix; permission matrix; package/user/UID matrix; filesystem/storage matrix; system-service matrix; IPC/Binder matrix; component/lifecycle matrix; resource/configuration matrix; graphics/surface matrix; native/ABI matrix; media/network/input matrix; white/black/partial reclassification; root-registry cross-match; genuinely new roots; environment blockers; runtime blockers; negative-test results; real-app evidence; remaining unknowns; recommended next foundation layer.
Do not hide gaps behind a high-level compatible label.

30. DEFINITION OF DONE

An unknown APK must be processable as: UNDERSTAND -> PREFLIGHT -> INSTALL -> IDENTITY -> PERMISSION -> SANDBOX -> SERVICES -> COMPONENTS -> LIFECYCLE -> RESOURCES -> EXECUTION -> RENDERING -> INPUT -> STATE -> PERSISTENCE -> REPEATABLE VERIFICATION.
MiniAndroid must explicitly say what the APK requires, what the runtime provides, what is missing, what is incompatible, what permission is required and whether granted, which package/user owns the operation, which service is missing, which ABI is executable, which storage is accessible, which component should start, which resource configuration is selected, whether graphics reached presentation, and exactly where first divergence occurred.
No app-specific hacks. No fake capability advertisement. No universal permission grants. No root/sandbox bypass. No process-survival-as-success. No APK-parse-as-execution. No non-empty-screenshot-as-success.
This is the Android foundation required before broad compatibility claims.

COMPLETENESS EXPANSION — DO NOT DECLARE BASE COMPLETE WITHOUT THESE LAYERS

The original sections above are necessary but NOT sufficient for a compatibility runtime. Before marking #374 complete, audit the following additional foundation layers. These are explicitly added because a runtime can pass Package/Permission/View checks while still being fundamentally non-Android-compatible underneath.

31. ANDROID RUNTIME / DEX EXECUTION CONTRACT

Audit the actual execution engine, not merely DEX parsing:

  • DEX header/version
  • class definition loading
  • class initialization /
  • instance/static fields
  • field identity by declaring class + field name + type semantics
  • instance/static methods
  • virtual/direct/static/interface/super dispatch
  • invoke-* semantics
  • return values
  • primitive/reference conversions
  • arrays and multidimensional arrays
  • object allocation
  • null behavior
  • exceptions and catch/finally
  • throw/rethrow
  • monitor-enter/exit
  • synchronized methods/blocks
  • method stack/frames
  • register lifetime
  • wide values
  • type checks
  • check-cast
  • instanceof
  • reflection
  • annotations
  • generic metadata where observable
  • class loaders
  • parent/delegation behavior
  • dynamic class loading
  • initialization ordering
  • circular initialization
  • verifier/type safety behavior
  • stack traces
  • Thread.currentThread identity
  • thread-local state
  • interruption
  • wait/notify/notifyAll
  • volatile visibility
  • atomicity
  • memory ordering
  • final-field semantics
  • GC reachability assumptions
  • object identity
  • identityHashCode
  • WeakReference/SoftReference/PhantomReference where used
  • finalization/cleanup semantics where applicable

The execution engine must distinguish:
PARSED / LOADED / INITIALIZED / EXECUTED / FAILED.

A method being found is NOT proof that its runtime semantics are correct.

32. JAVA/LIBCORE API FOUNDATION

Audit the Java-side platform surface underneath Android APIs:

  • java.lang
  • java.util
  • java.io
  • java.nio
  • java.net
  • java.security
  • javax.crypto
  • javax.net.ssl
  • XML parsing
  • regex
  • charset/Unicode
  • locale/ICU behavior
  • date/time
  • UUID
  • ZIP/JAR
  • streams
  • serialization where used
  • reflection
  • annotations
  • collections
  • concurrency
  • executors
  • atomics
  • locks
  • futures
  • random/security primitives

Do not implement only Android.* while the underlying Java contract is incomplete.

Record:
API_EXISTS / IMPLEMENTED / SEMANTICALLY_CORRECT / TESTED / REAL_APK_USED.

33. JNI / NATIVE BRIDGE CONTRACT

The native layer must be audited as a complete contract:

  • Java<->native method resolution
  • RegisterNatives
  • JNI_OnLoad
  • native method signatures
  • jobject/jclass/jstring/jarray handling
  • local/global/weak references
  • exception propagation
  • Get/Release primitive arrays
  • Get/Release string APIs
  • field/method ID lookup
  • monitor APIs
  • thread attach/detach
  • native-created threads
  • callback into Java
  • native thread identity
  • errno
  • signals
  • process exit
  • dlopen/dlsym/dlclose
  • TLS/native TLS
  • libc surface
  • pthreads
  • futex-like synchronization dependencies
  • file/socket syscalls used by native code

Native success must not be inferred from a library loading successfully.

34. PROCESS / ZYGOTE / APPLICATION STARTUP CONTRACT

Model the startup boundary explicitly:

APK install
-> package record
-> process selection
-> process creation
-> application class loader
-> Application object
-> attachBaseContext
-> ContentProvider initialization/order
-> Application.onCreate
-> component instantiation
-> lifecycle entry

Audit:

  • process names
  • isolated processes
  • shared processes where valid
  • fork/start semantics as applicable
  • environment setup
  • classpath
  • boot class path equivalent
  • application class loader
  • ApplicationInfo
  • instrumentation
  • startup providers
  • startup order
  • process death/restart
  • crash propagation

Do not start an Activity while silently skipping providers/Application initialization if the real platform would execute them.

35. THREADING / MEMORY / PROCESS RESOURCE CONTRACT

Audit:

  • thread creation/destruction
  • daemon/non-daemon behavior
  • thread names/priorities
  • scheduling
  • CPU starvation
  • synchronization
  • lock contention
  • deadlock behavior
  • memory allocation
  • heap limits
  • native heap
  • virtual address space
  • OOM behavior
  • allocation failure
  • stack limits
  • file descriptor limits
  • process limits
  • signal behavior
  • process kill
  • low-memory process eviction semantics where supported

A runtime that works only because it has unlimited host resources is not equivalent.

36. KERNEL / POSIX / LOW-LEVEL CONTRACT

Because Android is built on Linux, audit the subset actually required by the runtime and real APKs:

  • processes
  • threads
  • futex/synchronization primitives
  • signals
  • clocks
  • timers
  • epoll/select/poll
  • pipes
  • sockets
  • file descriptors
  • mmap/mprotect
  • shared memory
  • event mechanisms
  • filesystem semantics
  • permissions
  • symlinks
  • device nodes where required
  • proc/sys interfaces where observed
  • environment variables
  • resource limits

Do not claim full kernel compatibility. Produce a REQUIRED / PROVIDED / MISSING matrix based on observed APK/runtime dependencies.

37. HAL / HARDWARE ABSTRACTION BOUNDARY

Do not stop at Java service stubs.

For every hardware-backed capability classify:

APP API
-> framework service
-> Binder/IPC
-> native service
-> HAL/backend
-> host capability
-> result/error

Cover where relevant:

  • camera
  • audio
  • sensors
  • graphics
  • input
  • power
  • Bluetooth
  • Wi-Fi
  • location
  • USB
  • vibration
  • display

A Java API returning a plausible object is insufficient if the underlying operation cannot produce correct state/data.

38. BOOT / SYSTEM-SERVICE INITIALIZATION

Audit the runtime's equivalent of platform bootstrap:

  • system properties initialization
  • service registry initialization
  • core service startup order
  • PackageManager readiness
  • ActivityManager readiness
  • WindowManager readiness
  • permission/AppOps readiness
  • storage readiness
  • user/profile readiness
  • graphics/display readiness
  • network readiness
  • input readiness
  • media readiness

Define explicit readiness states and dependency ordering.

An app must not randomly succeed because a service happened to initialize first.

39. CLOCK / TIME / ALARM CONTRACT

Audit:

  • wall clock
  • monotonic clock
  • elapsed realtime
  • uptime
  • timezone
  • DST
  • locale
  • Calendar
  • java.time where supported
  • System.currentTimeMillis
  • System.nanoTime
  • Handler delays
  • AlarmManager semantics
  • timer ordering
  • clock changes
  • sleep/wake behavior

Time4J/Suntimes-style failures must be classified against this foundation rather than patched app-by-app.

40. POWER / BATTERY / DOZE-LIKE STATE

Audit the minimum platform model for:

  • battery level
  • charging state
  • battery saver
  • power manager
  • wake locks
  • screen state
  • idle/doze-like state
  • foreground/background state
  • process importance
  • throttling
  • suspend/resume semantics where relevant

Apps must receive coherent state transitions, not hard-coded battery values.

41. NOTIFICATION / BROADCAST / ALARM / JOB CONTRACT

Audit the generic scheduling/event plane:

  • broadcast registration
  • manifest receivers
  • ordered broadcasts where supported
  • sticky behavior where applicable
  • broadcast permission checks
  • implicit broadcast restrictions by API
  • PendingIntent identity
  • PendingIntent mutability/flags where applicable
  • alarms
  • exact/inexact behavior
  • alarm cancellation
  • JobScheduler
  • WorkManager interaction where observable
  • notification channels
  • notification permission
  • notification identity
  • cancellation/update semantics

42. URI / CONTENT / FILE PROVIDER SECURITY CONTRACT

Audit:

  • URI parsing
  • URI normalization
  • authority
  • path
  • query/fragment semantics
  • ContentResolver
  • provider resolution
  • provider permissions
  • path permissions
  • temporary URI grants
  • FLAG_GRANT_READ_URI_PERMISSION
  • FLAG_GRANT_WRITE_URI_PERMISSION
  • persistable URI permissions where applicable
  • FileProvider
  • content:// versus file:// behavior
  • canonical path checks
  • traversal protection
  • caller identity

43. DATABASE / SQLITE CONTRACT

Treat SQLite as a platform contract where Android APIs expose it:

  • SQLiteOpenHelper
  • SQLiteDatabase
  • transactions
  • WAL
  • locking
  • busy behavior
  • journal modes
  • cursor semantics
  • bind arguments
  • null/type conversion
  • schema versioning
  • onCreate/onUpgrade/onDowngrade
  • corruption/error behavior
  • concurrent access
  • close semantics
  • persistence across restart/reinstall
  • database path ownership

Do not classify "database file exists" as SQLite compatibility.

44. STORAGE / BACKUP / RESTORE / CLEAR-DATA SEMANTICS

Beyond basic files, audit:

  • clear app data
  • force stop
  • restart
  • reinstall
  • update in place
  • downgrade where applicable
  • backup eligibility
  • no_backup semantics
  • device-protected versus credential-protected data
  • cache eviction semantics
  • external app-specific storage
  • media/shared storage boundary
  • package removal cleanup
  • package replacement while data persists

The matrix must distinguish:
PERSIST / CLEAR / PRESERVE / REMOVE / UNKNOWN.

45. SIGNING / CERTIFICATE / PACKAGE TRUST

Audit:

  • APK signature parsing
  • signing scheme information
  • certificate identity
  • package signing identity
  • signature permission checks
  • shared UID compatibility
  • update compatibility
  • installer identity where relevant
  • package provenance
  • signature mismatch failures

APK parse success is not trust/installation success.

46. PACKAGE UPDATE / SPLIT / INSTALLER CONTRACT

Audit complete package lifecycle:

  • fresh install
  • update
  • split install
  • split removal/update
  • version comparison
  • downgrade rejection/handling
  • signature mismatch
  • native library extraction/update
  • resource split selection
  • code split selection
  • rollback/failure cleanup
  • atomicity of installation
  • partial-install rejection

47. APP VISIBILITY / QUERIES / CROSS-APP DISCOVERY

Audit Android package visibility semantics:

  • getInstalledPackages
  • getApplicationInfo
  • queryIntentActivities
  • queryIntentServices
  • resolveActivity
  • resolveService
  • provider discovery
  • package visibility restrictions
  • visibility exceptions
  • caller identity
  • permission effects

Do not expose every installed package by default.

48. COMPONENT SECURITY / PENDING INTENT

Audit:

  • exported defaults by API level
  • explicit component access
  • permission-protected components
  • receiver exposure
  • provider exposure
  • service exposure
  • PendingIntent creator identity
  • sender identity
  • mutability flags
  • one-shot/update/cancel semantics

"Complete Base" does NOT mean reimplement every internal Android class or every OEM-specific feature.

  • or proven to be an external prerequisite.
