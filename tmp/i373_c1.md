# WHITE/BLACK SCREEN — PREREQUISITE LAYER MUST BE EXPLICITLY PROVEN

Do not treat #373 as a documentation-only environment inventory. One of the highest-priority questions is whether the white/black/partial-loading symptoms are caused by an environment mismatch.

External evidence shows this is a real class of failure:
- ARM ABI can be advertised while no native translator exists; APK installs and only fails at launch.
- Waydroid explicitly carries native-bridge, ABI, graphics backend, gralloc, OpenGL ES and device properties as part of its runtime environment.
- SurfaceFlinger failures can arise from buffer/format/gralloc incompatibility and can result in black visual output.
- Display density/orientation are compositor/framework inputs, not cosmetic metadata.

Therefore run a dedicated WHITE-SCREEN PREREQUISITE AUDIT.

## WS-004 — CONTROLLED ENVIRONMENT TEST

Where technically feasible, vary ONE environment variable at a time:
API profile
density
resolution
orientation
ABI/native bridge
graphics backend
software renderer
refresh rate
feature declaration.

Do not modify multiple variables together.

If changing an environment parameter turns a white screen into real app content, that is causal evidence and must be recorded.

## WS-005 — DO NOT "FIX" BY SPOOFING EVERYTHING

Do not simply advertise:
all ABIs
all features
all GLES/Vulkan extensions
all sensors
all permissions
all API levels.

A declared capability must correspond to actual behavior.

False capability advertisement is itself a compatibility defect.

## WS-006 — WHITE-SCREEN SUCCESS CRITERION

A white-screen case is not fixed because:
- process stays alive,
- APK launches,
- screenshot is non-empty,
- PIL can read PNG,
- ViewTree exists,
- EGL initializes.

It is fixed only when the expected application-owned visual content reaches the capture path, with provenance, and when relevant interaction changes state/visual output.
