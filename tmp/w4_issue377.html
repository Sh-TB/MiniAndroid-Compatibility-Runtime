CONT-6 — External Root Knowledge Base Forensic Audit + Runtime Fan-out Validation

Canonical external knowledge snapshot

The latest supplied archive has now been independently inspected.

Current project HEAD at CONT-6 creation: 1c2ccdfd24957cef8affc4989dd439ccb30d7276

The latest archive DOES contain the claimed 5,434/5,976 dataset

Independent count of download/MiniAndroid_Root_Knowledge_Base.jsonl:

  • 5,976 total records
  • 5,434 VERIFIED-NEW
  • 274 VERIFIED-EXISTING
  • 266 PARTIAL-EXISTING
  • 2 REJECTED
  • 40 domain JSONL files
  • 5,976 unique IDs
  • 250 VERIFIED-NEW entries have empty test_apks
  • all rows are source/audit knowledge records; the VERIFIED-NEW label must NOT be interpreted as real-APK runtime proof
  • head is empty in the JSONL rows; use the archive INDEX/report's audited HEAD f8d4088b... as snapshot provenance
  • the archive's own human report states that existing registry roots were catalogued rather than independently re-verified in this audit.

The archive is therefore a legitimate and useful external discovery database, but it is NOT a ready-made 5,434-item runtime worklist.

CRITICAL ARTIFACT ACCESS CONTRACT

Do NOT paste the 6.5 MB JSONL into this Issue.

The full archive must remain available to the coder as a separate artifact. Use this priority order:

  1. Preferred permanent location: a dedicated repository research-data path, NOT root_registry.json, e.g.
    research/external-root-kb/current/MiniAndroid_Root_Audit_Archive.zip
    plus a small MANIFEST.md containing archive SHA-256, audit HEAD, record counts, and update date.
  2. If repository binary/data publication is not yet available: attach the exact ZIP to this Issue as a GitHub issue attachment and record its SHA-256 here.
  3. Never copy the full JSONL into the Issue body.
  4. Never merge these 5,434 findings into the runtime root registry merely because they exist in the KB.
  5. Future snapshots replace/update only the external KB artifact and manifest; the Issue remains the stable audit contract.
  6. Keep old snapshot hashes in a tiny history table so a later KB can always be compared against the previous one.

Future snapshot protocol

For every new archive:

new archive -> SHA256 -> record counts -> compare IDs -> compare semantic clusters -> compare current HEAD -> runtime validation -> only then promote selected roots

The coder MUST print the exact snapshot SHA it consumed at the beginning of every CONT-6 run.

REQUIRED WORKFLOW

Phase 0 — snapshot and current HEAD

  1. Read the external KB artifact directly.
  2. Verify archive SHA-256.
  3. Verify current main HEAD.
  4. Verify the archive's audited HEAD.
  5. Record stale-vs-current findings.
  6. Do not modify root_registry.json in the ingestion phase.

Phase 1 — forensic reconciliation

Classify every external candidate:

  • A = already covered by current registry
  • B = same root, additional evidence
  • C = existing semantic root but missing sub-law
  • D = genuinely new generic runtime/platform root
  • E = environment/prerequisite
  • F = source-only/reference/future/out-of-scope
  • X = duplicate/invalid/over-split/malformed

Mandatory:

  • exact ID uniqueness
  • semantic duplicates
  • original/source collisions
  • current registry overlap
  • already-fixed-at-current-HEAD findings
  • stale source references
  • source-only vs runtime-proven distinction
  • environment findings incorrectly counted as runtime roots.

Do NOT create 5,434 registry entries.

Phase 2 — semantic clustering

Collapse API/method-level observations into semantic laws.

Explicitly cluster:

  • Intent/Activity/Service/lifecycle families
  • Collections/ArrayList/Map/Iterator families
  • JNI slot families
  • View/ViewGroup families
  • Compose/Material3 families
  • WebView families
  • reflection families
  • NIO/security/crypto families
  • Kotlin/coroutines families
  • media/camera families
  • libGDX/game-engine families.

For each cluster:

  • raw findings
  • distinct semantic laws
  • current coverage
  • fan-out estimate
  • best real APK consumers
  • highest-confidence candidate root.

Raw row count MUST NOT be reported as independent root-cause count.

Phase 3 — highest-ROI runtime validation

Select approximately 20 high-confidence semantic clusters, not thousands of rows.

Selection priority:

  1. current white/black/partial frontiers
  2. games
  3. general apps
  4. high fan-out
  5. strongest source evidence
  6. independent consumer diversity.

Use approximately 10–20 real APK consumers total, including at least:

  • 3 games
  • 3 non-game apps
  • one previously white/partial title
  • one known-good regression control.

Phase 4 — six-game claim validation

The external audit claims these six built-in games reached REAL_APP_CONTENT:

  • 2048
  • mini-tetris
  • minicraft
  • snake-deluxe
  • snake-neon
  • tictactoe-deluxe

Validate independently at current HEAD where possible.

For every title record:

  • exact APK SHA
  • build provenance
  • install identity
  • ViewTree
  • draw operations
  • app-owned content provenance
  • pixel metrics
  • screenshot SHA
  • state/input evidence where applicable
  • 3 clean runs
  • first divergence if not successful.

Non-white pixels alone are NOT sufficient. A fixture/background/harness surface is not REAL_APP_CONTENT.

The archive's six-game result is a valuable hypothesis and acceptance candidate, not a current-HEAD fact until re-run.

Phase 5 — generic law and fan-out

For each confirmed law:

source -> law -> current divergence -> first runtime divergence -> generic fix/non-fix -> real APK -> 3 runs -> independent consumer -> fan-out

Measure:

  • titles improved
  • games improved
  • apps improved
  • visual/state/lifecycle/storage/media/native effect
  • regressions.

Do not claim “5,434 roots fixed”.

Phase 6 — registry promotion

Only C/D candidates can enter the normal registry.

Before adding anything:

  • full registry search
  • evidence-history search
  • current HEAD check
  • semantic duplicate check
  • external provenance attached
  • runtime proof attached separately.

The external KB remains a discovery/source artifact.

HARD RULES

  • No app-specific hacks.
  • No package-name conditionals.
  • No bulk 5,434-root implementation.
  • No registry pollution.
  • No source-only -> runtime-proven promotion.
  • No RESUMED/exit=0/PNG-only closure.
  • Preserve source -> law -> divergence -> runtime -> 3-run evidence discipline.
  • The external KB is a continuously growing searchlight, not the runtime registry.
