```
0x7f0f0056 -> type=3 str='M12,4.5C7,4.5 2.73,7.61 1,12c1.73,4.39 6,7.5 11,7.5s9.27,-3.11 11,-7.5c-1.73,-4.'
```

The `VectorRefResolver` seam — the callback the decoder uses to reach app resources — carried only `is_color`/`argb` and `bytes`/`path`/`density`. **There was no way to return a string.** So the decoder read an empty attribute and correctly reported a parse failure. The bug is architectural: the resolver contract could not express the answer even though the ARSC had it.

1. `VectorImageRef` gains `is_string` + `str_value` (`src/renderer/software_renderer.h`).

3. The decoder, on an empty `pathData` that is a reference, asks the resolver for the payload before declaring failure (`src/renderer/vector_decode.cpp`).

### AOSP law implemented

`canvas.clipPath()` is a **stateful canvas operation**, not a sibling-local property. So a clip:

- constrains every **later** sibling in the same group and their descendants,
- does **not** affect earlier siblings,
- does **not** leak to a sibling outside the group.

The implementation threads a running clip set through `walk()` per group, stores the clip in force on each `VPath`, rasterizes it into a non-zero winding coverage mask, and gates every paint op through that mask. The clip's own `pathData` goes through the same resolver seam as `<path>`, so aapt2-hoisted clip paths resolve too.

Investigating the reference showed why:

```
0x7f08005c: BRANCH=string str='res/Cb.xml'  <-- drawable file never extracted
0x7f080000: BRANCH=string str='res/cc.xml'  <-- drawable file never extracted
```

`ExecutionEngine::image_ref_resolver()` claimed **every** `TYPE_STRING` row as a pathData payload:

```cpp
if (val && val->is_string() && !val->string_value.empty()) {

```

aapt2 also stores **drawable** references this way, with the payload being a zip entry path. That branch returned before `select_file()` ever ran, so `ref.bytes` stayed empty. This is why `<animated-vector android:drawable>` could never resolve — and it left `<adaptive-icon>` layer references exposed to exactly the same failure, since `decode_adaptive_icon()` consumes `ref.bytes`.

### Root cause

1. `decode_vector_drawable()` only accepted `root.name == "vector"`; `animated-vector` fell through to the generic unsupported-root error.
2. The resolver used the **type** of a table row to decide what it meant, but aapt2 uses `TYPE_STRING` for two different things: inline pathData payloads *and* file references.

### Fix

**AVD still frame.** AOSP `AnimatedVectorDrawable.getConstantState()` builds its `VectorDrawable` from `android:drawable`, and `VectorDrawable.draw()` paints whatever the *current* property values are. So the honest still frame is the referenced VD rendered with its **own declared attributes** — not a frame synthesised from an animator's `start` values, which is the tempting wrong answer (it would also be wrong for any animation mid-flight).

Root-level `<target>`/`<objectAnimator>` carry no paint and are consumed rather than walked. Depth-guarded against cycles.

**Resolver.** A string row whose payload is a `res/*.xml` entry is a *file*, so it now takes the file branch and extracts the bytes:

```cpp
const bool looks_like_entry =
    sv.rfind("res/", 0) == 0 &&
    (sv.size() > 4 && sv.compare(sv.size() - 4, 4, ".xml") == 0);
```

This is a shared fix at the resolver layer, not an AVD-specific hack: it repairs drawable reference resolution for every consumer.

**Status:** root-caused, fixed, measured on real APKs, committed locally (`9558fc1c`). Push still blocked by the same credential limitation documented in §7 of the MG-012 report.
**Domain:** `resource/asset` · **Upstream law:** `LayerDrawable.inflate`/`draw`, `StateListDrawable.inflate`/`onStateChange`, `ColorStateList`.

I picked up #634 because its own corpus scan still listed live drawable failures after the MG-012 fix landed. Investigating those turned up **four** distinct defects, one of which is a hole in the MG-012 resolver change itself.

---

### Defect 1 — the MG-012 resolver fix only recognised `.xml`

MG-012 taught the resolver that a `TYPE_STRING` row whose payload is a zip path is a *file*, but tested the path with a `.xml` suffix:

```cpp
const bool looks_like_entry =
    sv.rfind("res/", 0) == 0 &&
    (sv.size() > 4 && sv.compare(sv.size() - 4, 4, ".xml") == 0);
```

aapt2 stores **bitmap** drawables the same way. Measured directly:

```
0x7f08007b: string='res/90.png' looks_like_entry=0 -> CLAIMED AS STRING PAYLOAD (no bytes!)
0x7f080079: string='res/xR.png' looks_like_entry=0 -> CLAIMED AS STRING PAYLOAD (no bytes!)
```

So every `<bitmap android:src="@drawable/x">` reference still returned an empty `bytes` buffer. The honest test is not a suffix — it is *does this APK ship that entry*:

```cpp
if (sv.rfind("res/", 0) == 0) {
    auto entry_bytes = apk_parser_.extract_entry_cached(sv);
    if (!entry_bytes.empty()) { /* file branch */ }
}
```

### Defect 2 (MG-014) — `<layer-list>` is a compositing container, not a selector

`layer-list` was routed into the state-list first-match branch. A `LayerDrawable` has no first-match rule and no default item: `inflate` walks every `<item>` and `draw` paints them in document order. The wrong branch made the failure certain:

```
res/Jl.xml  -> FAIL  state-list: no default (state-less) item matched
res/Kv.xml  -> FAIL  state-list: no default (state-less) item matched
```

There is now a dedicated `decode_layer_list()` that composites every layer over the accumulated buffer. It also accepts the **nested-child** item form (`<item><bitmap android:src=…></item>`), which is what aapt2 emits for bitmap layers, and it reports an empty `<layer-list/>` by name instead of pretending it is a selector miss.

### Defect 3 (MG-015) — state matching skipped every stateful item

This was the widest bug. The old loop treated *any* `state_*` attribute as disqualifying:

```cpp
bool stateful = false;
for (const auto& at : item.attributes)
    if (at.name.rfind("state_", 0) == 0) stateful = true;
if (stateful) continue;
```

`StateListDrawable.inflate` does not work that way. It records `stateSet[count++] = a.getBoolean(i,false) ? resId : -resId` and `onStateChange` picks the **first item whose whole set matches** the current state. A default, idle view *is* enabled, so `state_enabled="true"` must match. With the old code, a selector whose items were all stateful had no candidate at all — which is exactly what an enabled/disabled button background looks like. Whole app affected:

```
de.duenndns.gmdice_11.apk   BEFORE  total=3 ok=0 fail=3
                            AFTER   total=3 ok=3 fail=0
```

Matching is now against the default view state (enabled; not focused / pressed / selected / checked / activated / hovered), and the fallback verdict was renamed to `no item matched the default view state` because the old wording described a law that was never implemented.

### Defect 4 (MG-016) — colour state lists carry `android:color`

`res/color/*.xml` items do not have `android:drawable`. They carry `android:color`, resolved as an app-package reference (verified `type=2 is_ref=1`). Ignoring that made **150 items** across the corpus unreachable, taking out the tint/text-colour layer of every themed widget. A matching item now yields a solid raster and `color_type_name = "<root>-color->rgba"`.

A resource id's top byte names its package. **`0x01` is framework-res**, which ships in `framework-res.apk` and is *never* inside an app APK.

Every one of the selectors above has an item whose drawable is a **framework colour**, e.g.

```xml
<selector>
  <item state_selected="true" drawable="@drawable/..."/>

</selector>
```

`ArscParser::resolve_full()` walks the reference chain, asks the app table for `0x0106000d`, gets nothing, and returns `MISSING_REFERENCE_TARGET`. That is **not** a resolver-quality problem — a single-table resolver can never answer it, no matter how correct the rest of the code is. AOSP solves this with AssetManager2's multi-package table set. We have no `framework-res.apk` (hard constraint: no AOSP source/system builds), so this had to be a fallback tier.

The project already has exactly this pattern for theme attrs (`FRAMEWORK_THEME_ATTRS`, generated from AOSP law files with recorded SHAs). I added the same tier for colours.

## MG-023 — `<ripple>` and `<bitmap>` as ROOT drawable documents

Continuing the vector-drawable stream on **#634**. This round was driven by the committed census harness, not by guessing: I rebuilt `drawable_census_probe` against the real APK corpus, then worked the failure list top-down.

### What was broken

After MG-022 the census showed these remaining failures in `org.secuso.privacyfriendlymemory_100`:

```
4  vector: root element <objectAnimator> unsupported
3  vector pathData parse failure
2  animated-vector: vector pathData parse failure
1  vector: root element <bitmap> unsupported
1  vector: root element <ripple> unsupported   (x4 in total, variously prefixed)
1  selector: no item matched the default view state
...
```

Two distinct defects sat behind that list.

**1. The census harness itself was lying (probe defect, not runtime).** The `pathData parse failure` entries were a *measurement* bug. `aapt2` hoists a large `pathData` into `resources.arsc` as a **`TYPE_STRING`** and leaves a reference in the AXML. The runtime resolver handles that (`ref.is_string`), but the census probe's resolver only accepted a string payload if it started with `res/` — treating every hoisted path as a missing file. So the probe reported 3+2 failures that the real engine did not have.

**2. `<ripple>` and `<bitmap>` were only known as *children*.** `RippleDrawable` and `BitmapDrawable` are ordinary standalone drawable documents, and `aapt2` emits them as such. The decoder knew `<bitmap>` only as a child of `layer-list`/`selector`, so any drawable whose **root** element was `<bitmap>` or `<ripple>` fell through to:

```
vector: root element <bitmap> unsupported
```

and painted nothing. This is the shared-runtime gap, not an app quirk: `notification_tile_bg` (`res/Cv.xml`, `<bitmap src=… tileMode=1>`) is a plain AOSP `BitmapDrawable`.

### Root cause

`decode_drawable_element()` dispatched on `root.name` over a fixed list (`adaptive-icon`, `shape`, `inset`/`scale`/`clip`/`rotate`, `layer-list`, `selector`/`level-list`/`animated-selector`, `animated-vector`, `vector`). `<ripple>` and `<bitmap>`/`<nine-patch>` were absent from that list, so the `root.name != "vector"` fallthrough produced the generic "unsupported" error. The child-only handling inside `decode_layer_list`/selector never runs for a top-level document.

### What I changed

`src/renderer/vector_decode.cpp`:

- **`<ripple>` (new root branch).** Paints its content `<item>`, skipping `@android:id/mask` (which only shapes the transient press animation). The content item may carry its drawable either as `android:drawable` (a reference) **or** as a nested child element (`<selector>`/`<shape>`/…), exactly like a layer-list item — decoding the `<item>` itself would fail with `root element <item> unsupported` (`res/yP.xml`).
- **`<bitmap>` / `<nine-patch>` (new root branch).** Resolves `android:src` and decodes the image entry via the existing `decode_image_bytes` path.
- `ripple` added to the single-child wrapper list so a nested `<ripple>` inside `<inset>`/`<scale>` resolves.

`tests/drawable_census_probe.cpp`: resolver now mirrors `ExecutionEngine` — a non-`res/`-prefixed string payload is a literal `TYPE_STRING`, not a missing file.

An honest note on the ripple colour-only case: all four ripple drawables in this APK are **colour-only** (`android:color` with no `<item>`). AOSP builds those as a valid `RippleDrawable` that paints nothing until pressed. Rather than fake pixels, the decoder now names that condition:

```
ripple: colour-only RippleDrawable (no content <item>) — paints nothing until pressed, not a decode failure
```

which is a truthful classification, not a "fixed" render. The genuinely-rendering win this round is `<bitmap>` and the ripple-with-content path.

Not a guess — from `TransitionDrawable.draw`

```java
private int mAlpha = 0;                    // field initialiser
...
```

At rest `mAlpha == 0`, so **only layer 0 is drawn**. Layer 1 stays invisible
